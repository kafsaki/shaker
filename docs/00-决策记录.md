## ADR-001 产品形态

**结论**：结构化配方库 + 可视化调酒播放器 + UGC 社区。

差异点不是"又一个菜谱站"，而是**任何人写的配方都能自动生成一段调制动画**。

主要区域：

| 区域 | 内容 |
| --- | --- |
| 探索 | 热门 / 最新 / 关注 三条 Feed + 多维筛选（基酒、手法、酒精度、口味、杯型） |
| 配方页 | 分步动画播放器（可拖时间轴、单步回看）+ 文字步骤 + 原料卡 + 评论 |
| 原料百科 | 14 类品类图谱，每个原料页反查"用到它的配方" |
| 创作 | 结构化编辑器（左选原料/步骤，右实时预览动画） |
| 我的 | 酒单管理、关注/粉丝、草稿、通知 |

## ADR-002 架构基石：配方 IR

**结论**：配方存成带 `schemaVersion` 的结构化 JSON 文档（Recipe IR），只引用 ID，不内联样式。动画是 IR 的纯函数投影。

规范见 `01-配方IR规范.md`。

**理由**：这一条决定了其它一切。有了 IR：

1. 需求 6（文字转配方）退化成"让模型输出一份合法 IR"——有 schema 可校验，不是自由生成。
2. Feed 封面图/OG 图可以跑同一套代码生成，不用美工逐张出图。
3. 三端只有最后的绘制层不同，物理与配色逻辑共用。
4. 经典页的"规格分布图"、两份配方的"并排 diff"等功能几乎零成本白拿（见 ADR-010）。

**关键纪律**：动作词表、原料、杯型、冰型**必须是闭集枚举**。这是动画能自动生成的前提，也是 v2 让模型产出 IR 的前提。

## ADR-003 后端：Go

**结论**：Go 1.27 + chi + huma v2 + pgx/sqlc + river。

```
HTTP        chi              标准库风格，net/http 兼容
OpenAPI     huma v2          code-first，自动产出 spec + 请求校验
DB          pgx v5 + sqlc    不用 ORM——写真 SQL，生成类型安全 Go 函数
迁移        goose            纯 SQL 文件
IR 校验     santhosh-tekuri/jsonschema/v6 + go:embed
认证        golang-jwt/v5 + argon2id
任务队列    river            Postgres 原生，省掉 Redis
对象存储    aws-sdk-go-v2/s3 MinIO 兼容
日志        log/slog         标准库
```

**理由**：

- 决策过程中曾先定 TypeScript，理由是"一份 zod schema 前后端共享"。该理由基于一个错误假设：**后端需要完整建模 IR。它不需要。** 后端对 `ir` 这个 JSONB 字段只做三件事：写入时校验合法性（JSON Schema 即可，不需要 Go struct）、提取 `ingredients[]` 投影进 `recipe_ingredients`、算几个派生值。存取全程当不透明 JSONB 传递。
- 性能**不构成选型理由**。动画全在客户端算、封面图客户端截帧上传，后端职责就是"在 Postgres 前面吐 JSON"——最不吃 CPU 的负载。瓶颈必然出现在 Postgres 查询计划、缺失索引、N+1 上，与语言运行时无关。
- 同理，"先用 Node 起步、遇到瓶颈用 Go 补热点"这条退路**不应作为决策依据**：真到那天你有用户有数据，是最不敢动架构的时候；且瓶颈在 Postgres，换语言不解决；拆服务补热点引入的分布式复杂度远超收益。
- 真实差异只剩：Go 赢在运维成本（单二进制 ~20MB）、依赖稳定性（标准库极稳，三年后大概率还能直接 build）、复杂查询体验（sqlc 写真 SQL 拿类型安全，优于 ORM）；TS 赢在心智统一、IR 零桥接、v2 AI 生态更厚。
- 最终由"作者愿意长期写哪个"定夺。**v1 最大的风险不是性能，是做不完。**

**代价与缓解**：

| 代价 | 缓解 |
| --- | --- |
| IR 校验需 JSON Schema 桥 | `z.toJSONSchema()` 生成 → `go:embed` 读取 → CI diff 防漂移。约半天 |
| v2 AI 编排生态较薄 | `anthropic-sdk-go` 官方维护；国产模型多有 OpenAI 兼容接口。真别扭时把 `ir-extractor` 拆成无状态 TS 小服务，代价极低 |
| 两条工具链 | Makefile / Taskfile 统一入口 |

## ADR-004 前端：Nuxt 4 + Vue 3

**结论**：Nuxt 4 + Vue 3 + Tailwind + shadcn-vue（底层 Reka UI）+ Pinia + @tanstack/vue-query。

**理由**：

- 作者已有 Vue 项目，熟悉度是真实优势；这个项目没有任何一项需求是 React 独占的。
- 对**编辑器 + 实时动画预览**这个核心场景，Vue 的细粒度响应式更顺手：改一个用量就重算时间轴，在 Vue 里是自然的，在 React 里要跟 `useMemo`/`useCallback` 搏斗。
- 项目全部难点都在 `recipe-ir` / `animator-core` / `api-client` 三个**纯 TypeScript、零 UI 依赖**的包里。前端框架只负责把算好的关键帧画出来，所以换框架换的是外壳不是内核。

## ADR-005 移动端：二期，消费优先，框架待实测

**结论**：v1 只做 Web/PWA。移动 App 二期，**独立设计 UI**，**消费优先**（发布与编辑留在 Web）。框架由动画原型实测决定。

移动端需要独立设计的部分：

| | Web | App |
| --- | --- | --- |
| 导航 | 顶栏 + 侧边 | 底部 Tab + 手势返回 |
| 播放器 | 卡片内嵌，鼠标拖时间轴 | 全屏竖版，时间轴放拇指热区（下半屏） |
| 浏览 | 网格瀑布流 | 全屏沉浸式上下滑，一屏一杯酒 |
| 编辑器 | 左右分栏实时预览 | 分步向导，一屏一步 |
| 原生能力 | — | 分享 sheet、推送、酒单离线缓存 |

**"一屏一杯酒上下滑"是 App 存在的理由**——调酒动画天生适合这个形态，是移动端能做出**优于** Web 的体验的地方，不是妥协版 Web。

**消费优先的理由**：结构化编辑器在手机上做全功能极难；且发布行为天然发生在电脑前。这个裁剪让任何技术选型都轻松一大截。

**框架候选与决策标准**：

| 候选 | 优势 | 风险 |
| --- | --- | --- |
| **A. Capacitor + Ionic Vue** | 复用 Vue 技能；`animator-web` 渲染器原样跑（WebView 即浏览器），一套渲染器两端用；Ionic 提供真正的原生导航栈/侧滑/动量滚动 | WebView 里 Canvas 2D 粒子能否在中端安卓机稳住 60fps |
| **B. Expo + RN + react-native-skia** | 真原生，Skia 是画液体粒子的最佳工具，性能上限高；EAS 热更新 | 需多写 `animator-skia` 绘制后端（约 300 行）；Vue/React 两套 UI 写法并存 |

**决策标准**：动画原型做完后丢进安卓 WebView，在中端真机跑 Daiquiri 硬摇 + Mojito 气泡场景。稳住 60fps → A；明显掉帧 → B。

**不选 Flutter**：`animator-core` 得用 Dart 重写，两份实现必然长期发散出 bug。退化成"服务端编译 Timeline + Flutter 只做播放器"则移动端编辑器无法实时预览。**不选 NativeScript-Vue**：生态太小。

## ADR-006 基础设施：v1 仅 Postgres + MinIO

**结论**：本地 Docker Compose 起 Postgres 17 + MinIO。**v1 不引入 Redis。** 存储走 S3 兼容接口，之后换云不改代码。

**理由**：

- 队列用 **river**（Postgres 原生），不需要 Redis。
- Feed 与计数在 v1 规模下 Postgres 自己够：`ORDER BY hot_score DESC LIMIT 20` 配索引，十万级配方内瞬时返回；计数用原子 `UPDATE` 即可，不需要 Redis 抗写。
- 真测出瓶颈再加 Redis。不提前加。

**待办**：本机当前**未安装 Docker**，需装 Docker Desktop 或原生 Postgres。不阻塞 IR/前端工作。

## ADR-008 AI 能力（需求 6、7）：二期

**结论**：v1 不做。v2 倾向**平台默认额度 + BYOK 进阶**，而非纯 BYOK。

**纯 BYOK 的两个问题**：

1. **会让需求 6/7 的产品目的落空**。需求 6 的价值就是降低发布门槛，但要求用户先申请模型 key 再填进设置页，门槛比老实填表更高。需求 7 的 bot 是给**新访客**探索用的，访客不可能有 key，作为产品亮点直接废掉。
2. **合规责任转移不掉多少**。BYOK 能省的是"平台作为生成式 AI 服务提供者"的备案义务；但用户拿自己的 key 生成内容、再发布到本站，**发布内容的审核责任仍在平台**。

**建议形态**：平台侧配国产模型 + 自己的 key，设死额度（如每人每日 3 次文字转配方、10 轮 bot 对话）——单次文字转配方仅几千 token，国产模型成本近乎可忽略。想无限用/换模型的去设置页填自己的 key。**新用户零门槛尝到，重度用户自己出钱。**

**v1 唯一需要为此付出的成本：零。** 只要保持 IR 用 zod 写、动作/原料/杯型是闭集 enum——这本来就是 ADR-002 的要求。

**v2 的技术核心**是一个**与模型无关的结构化输出适配层**（国产模型间 structured output 能力差异很大，不能依赖某家的 native tool use）：

```
packages/ir-extractor
  extractRecipeIR(text, { provider, model, apiKey })
    ├ 两段式：先抽自由文本提到的原料/动作 → 后端对齐到真实 ID → 再组装 IR
    ├ 约束：prompt + 由 zod 导出的 JSON Schema + few-shot，不依赖 native tool use
    ├ 修复环：zod safeParse 失败 → 把校验错误回灌给模型重试（上限 2 轮）
    └ 降级：仍失败则返回部分 IR + unresolved[]，丢进编辑器让用户手填
```

**降级路径必须存在。AI 永远只是编辑器的加速器，不是唯一入口。** 这也正说明 v1 先做扎实的手动编辑器是对的顺序。

**需求 6 在移动端价值更大**：手机上做不了精细分栏编辑器，但"打一段话 → 自动生成 IR → 确认几项 → 发布"在手机上比在电脑上更自然。

## ADR-009 原料分类：品类 / 角色 双轴

**结论**：两个正交的轴。

- **品类（是什么）**——稳定不变，挂在 `ingredients.category`，用于百科导航与筛选
- **角色（在这杯里干什么）**——同一原料在不同配方里角色不同（金酒在 Martini 是基酒，在 Long Island 只是修饰料之一），所以必须挂在 `recipe_ingredients.role`

**理由（需求文档原分类"基酒、利口酒、软饮、香料"的四个硬伤）**：

1. **加强/加香葡萄酒无处安放**。味美思既不是基酒、不是利口酒、不是软饮、更不是香料——但它是 Dry Martini、Manhattan、Negroni、Martinez 的核心。同类还有雪莉、波特、Lillet。这一整类缺失，最重要的一批经典配方录不进来。
2. **苦精与苦味利口酒必须拆开**。不是学术洁癖，是数据模型问题：

   | | 例子 | 计量 | 动画表现 |
   | --- | --- | --- | --- |
   | 调酒苦精 bitters | Angostura、Peychaud's | **2 dash**（几滴） | 几乎不影响液面，只贡献色调 |
   | 苦味利口酒 amaro | Campari、Aperol、Fernet | **30 ml** | 主料，鲜艳色，显著液面层 |

   混成一类，`unit` 枚举与液面计算会直接错乱。
3. **冰必须是独立品类**。冰型是动画的一等公民：碎冰是雪泥质感、球冰是单个大球、冰柱是长条、crushed 让液体变浑浊。原料表里不给冰一个位置，动画就没法自动生成。
4. **品类 ≠ 功能角色**（见上）。这是原分类最根本的问题。

**一级品类 14 类（决定不压缩）**：

| 品类 | 二级示例 | 动画相关性 |
| --- | --- | --- |
| `spirit` 烈酒 | 金酒/伏特加/朗姆/龙舌兰·梅斯卡尔/威士忌/白兰地/白酒·烧酎 | 透明或琥珀，低粘度 |
| `liqueur` 利口酒 | 橙味/草本/果味/咖啡坚果/乳脂/花香/茴香 | 高饱和色，中高粘度，密度大→分层 |
| `amaro_bitter` 苦味酒与苦精 | 苦味利口酒（ml）/ 调酒苦精（dash） | 两种行为，见上表 |
| `fortified_wine` 加强·加香酒 | 味美思/开胃酒/雪莉/波特/马德拉 | ← 原分类缺失 |
| `wine_beer` 葡萄酒与啤酒 | 起泡酒/静态葡萄酒/啤酒/苹果酒/清酒 | 起泡酒 `carbonated` |
| `juice` 果汁 | 柑橘类（酸味核心）/其他果汁/蔬菜汁 | 柑橘略浑浊，番茄汁高不透明 |
| `syrup_sweetener` 糖浆与甜味剂 | 糖浆/杏仁 orgeat/石榴 grenadine/蜂蜜·龙舌兰蜜 | 高粘度→倒注慢；grenadine 密度大→沉底渐变 |
| `mixer` 软饮与调和饮料 | 苏打水/汤力水/姜汁汽水·姜啤/可乐 | 全部 `carbonated`，气泡发射器 |
| `dairy_egg` 乳制品与蛋 | 奶油/牛奶/椰浆/蛋清 | 蛋清 → `texture: foam`，干摇出泡沫层 |
| `coffee_tea` 咖啡与茶 | 浓缩咖啡/冷萃/茶汤 | Espresso Martini 的咖啡泡沫冠 |
| `spice_herb` 香料与草本 | 鲜草本（可 muddle）/干香料/杯口盐糖/酊剂喷雾 | ← 原分类"香料"只覆盖到这一类 |
| `garnish` 装饰物 | 柑橘皮卷·圆片·角/樱桃·橄榄·珍珠洋葱/脱水片/食用花 | 图标叠加 + 位置枚举 |
| `ice` 冰 | 方冰/大方冰/球冰/碎冰/裂冰/冰柱/干冰 | ← 驱动动画，必须独立 |
| `other` 其他·现代原料 | 泡沫剂/酸溶液/盐水/清水 | 澄清、酸度调整等现代技法 |

**不压缩到 9 类的理由**：原料百科正是需求 1 的主体，分得细是加分项；且合并 `amaro_bitter` 会重新引入计量混乱。

**置信度说明**：`ingredients.category` 这一层有物理依据（密度、含气、粘度、计量单位），不是审美问题，置信度高。

## ADR-010 鸡尾酒分类：家族做主轴，IBA 做徽章

**结论**：

- **不用 IBA 三档做分类导航**，但存 `iba_category` 字段作为权威徽章 + 种子数据来源
- **主分类用鸡尾酒家族 `family`**
- 再叠自由 `tags`（口味、场景、季节）做软性发现

**理由**：

IBA 官方鸡尾酒表分三档——The Unforgettables / Contemporary Classics / New Era Drinks，2020 年改版后约 90 款（**做种子数据前需核对当前官方名单，数量与条目待验证**）。问题是这三档是**历史地位的策展，不是分类法**。"Unforgettables"不告诉用户这杯什么味道、怎么做。没人会按"这杯酒有多老"来找酒喝。

IBA 的真正价值在三处：

1. **完美的冷启动内容源**——约 90 款公认经典 + 官方配比。配比属公开事实不受版权保护，文字描述我们自己重写。
2. **权威徽章**——配方页打"IBA 官方配方"标记，对新站公信力很有用。
3. **收录优先级排序。**

**家族才是调酒师实际在用的分类**：

| 家族 | 结构 | 代表 |
| --- | --- | --- |
| `sour` 酸酒 | 烈酒 + 柑橘 + 糖 | Daiquiri、Margarita、Whiskey Sour、Sidecar |
| `fizz_collins` 菲兹·柯林斯 | 酸酒 + 苏打 | Gin Fizz、Tom Collins、Ramos |
| `old_fashioned` 古典 | 烈酒 + 糖 + 苦精 | Old Fashioned、Sazerac |
| `martini_duo` 马天尼型 | 烈酒 + 加香酒 | Dry Martini、Manhattan、Martinez、Vesper |
| `equal_parts` 等份型 | 等比多料 | Negroni、Last Word、Paper Plane |
| `highball` 高球 | 烈酒 + 软饮 | Gin Tonic、Moscow Mule、Cuba Libre、Paloma |
| `smash_julep` 捣压类 | 鲜草本/水果 muddle | Mojito、Mint Julep、Caipirinha、Bramble |
| `punch_tiki` 潘趣·提基 | 多朗姆 + 果汁 + 糖浆 | Mai Tai、Zombie、Jungle Bird |
| `flip_creamy` 蛋奶类 | 蛋/乳脂 | Alexander、Grasshopper、Piña Colada |
| `spritz_wine` 起泡·葡萄酒基 | 葡萄酒/起泡酒为主 | Spritz、Bellini、Mimosa、French 75 |
| `hot` 热饮 | 热基底 | Irish Coffee、Hot Toddy |
| `layered_shot` 分层·子弹 | 密度分层 | B-52 |

**家族对本项目格外合适：家族 ≈ 一套动画模板。** Sour 必然是"摇壶 + 冰 + 硬摇 + 细滤 + 碟型杯"；Highball 必然是"杯中直调 + 加冰 + 补气泡"；Smash 必然带 muddle。所以 `family` 同时是导航维度**和编辑器的动画预设入口**——用户选"我要做一杯 sour"，编辑器直接铺好五步骨架，他只填原料。

**这对需求 3（降低发布门槛）的价值可能比 AI 自动生成还大，且零成本。**

**置信度说明**：**家族边界在业内本身有争议**（Mojito 算 smash 还是 highball、Gin Fizz 算 sour 还是自成一家，没有唯一权威）。所以 `family` 做成**可空、单选、运营可改**的编辑性字段，不做硬约束——它主要服务导航与动画预设，边界模糊不影响系统正确性。

## ADR-011 双语：词表强制，UGC 单语

**结论**：

- 我们自己维护的**受控词表**（原料、杯型、技法、标签）强制双语 `name_zh` + `name_en`
- 用户写的**配方标题与描述单语 + `lang` 字段标记**
- **v1 不做 UI i18n**

**理由**：

- 调酒领域英文名是事实标准（Cointreau、Angostura、orgeat 很多没有稳定中译），词表双语现在做很便宜，后面加很贵。
- **要求用户双语发布是荒谬的，会直接掐死发布量。**
- 双语数据字段 ≠ 全站双语 UI。v1 界面只中文，但原料卡中文为主英文小字为辅（`Cointreau 君度` 这种排版）——这本身就是调酒站该有的样子。等真要做英文站时数据层已就绪，只补 UI 层。

## ADR-012 搜索：pg_trgm 主力

**结论**：`pg_trgm` 主力 + 英文长文 `to_tsvector('english', ...)` + `pgvector` 留位（v2 语义搜索）。

**理由**：

- 中文全文检索的 `zhparser` / `pg_bigm` 都要自己编译，在本地 Docker 里很折腾。
- `pg_trgm` 是 postgres contrib 自带、零额外扩展，中英通吃，天然支持拼写容错与部分匹配。需求 4 的四种搜索（配方名、酒名、用户名、原料名）全是**短词场景**，trgm 表现很好。
- 十万级配方以内不需要 ES。**现在上 ES 是过度设计。**

## ADR-013 配方变体：经典锚点 / 创作血缘 双机制

**结论**：两个互不干扰的机制，可同时存在也可都为空。

```sql
classic_key  text                          -- 'daiquiri'，经典锚点
derived_from uuid REFERENCES recipes(id)   -- 创作血缘
is_canonical boolean DEFAULT false         -- 官方权威条目
CREATE UNIQUE INDEX ON recipes(classic_key) WHERE is_canonical;
```

**理由**："变体"其实是两件不同的事，合起来想才会纠结：

| | 情形 | 用户检索意图 | 组织方式 |
| --- | --- | --- | --- |
| **(a) 同名经典的不同规格** | 还是 Daiquiri，糖从 15ml 减到 10ml | "Daiquiri 怎么做" | 聚合到经典条目下 → `classic_key` |
| **(b) 基于经典的原创** | 朗姆换梅斯卡尔 + 加辣椒，名"Smoky Devil" | 找新作品 | 独立配方 + 标注血缘 → `derived_from` |

把 (b) 埋进 Daiquiri 页面是埋没作品；把 (a) 放成 100 条独立配方，首页和搜索会被同质内容淹死——**这是 UGC 菜谱站最经典的死法**。

**经典条目复用 `recipes` 表**，不建第二套模型（`author_id` 指向官方账号，`is_canonical = true`）。这样经典配方白拿全部基础设施：IR、动画、评论、点赞、加入酒单。v1 经典条目只有运营能改；wiki 式协作编辑是 v2 的事（`recipe_revisions` 已支持）。

**classic_key 判定三层，绝不做自动强制判定**：

1. 作者发布时自己选（编辑器搜经典列表）
2. 系统给**建议**：标题含 "Daiquiri"，或原料骨架与某经典高度重合 → 提示挂载，用户确认
3. 运营可改

算法判"这是不是 Daiquiri"必然出错且有争议——加了 maraschino 就变成 Hemingway Daiquiri，那还算 Daiquiri 吗？这种边界让人来定。

**真正解决淹没问题的是 Feed 层规则，不是数据层**（放在 Feed 层的好处是调参便宜，数据模型不动）：

- `/feed/hot`、`/feed/new`：同一 `classic_key` 在单个分页窗口内**最多 2 条**，其余折叠为"另有 125 个 Daiquiri 变体 →"
- 搜索 "Daiquiri"：权威条目置顶，下方分组"社区变体 (127)"按热度排
- 配方页显示"衍生自 X"与"被 N 人改编"

**IR 白拿的产品亮点**（普通菜谱站做不到，实现成本几乎为零）：

- **规格分布图**：127 个 Daiquiri 变体的朗姆/青柠/糖比例散点或箱线图，一眼看出社区共识落点、自己的配方偏甜还是偏酸
- **并排 diff**：两份配方的 IR 差异对比

## ADR-014 用量单位：原始值 + 归一化值双存

**结论**：

```ts
{ amount: 2, unit: "oz", amountMl: 59.15 }   // amountMl 为派生值，可空
```

- **`amount` + `unit` 是真相源**，展示优先用它
- **`amountMl` 是派生的归一化值**，用于液面高度、ABV 估算、总量校验、按份缩放；不可换算单位为 `null`

**理由（单存任何一个都坏）**：

- **只存 ml**：美式配方原生是 `2 oz / ¾ oz / ½ oz`，存成 `59.15 / 22.18 / 14.79` 既丑又失真——作者意图是"2 oz"这个整数。
- **只存原始**：液面高度、ABV、杯容量校验全都算不了。

**不可换算单位的处理**：

| 单位 | 类型 | `amountMl` | 液面贡献 | 显示 |
| --- | --- | --- | --- | --- |
| `ml` `cl` `oz` | 体积 | 精确换算 | 全额 | 按用户偏好 |
| `dash` | 准体积 | ≈ 0.6 ml（约定） | **忽略，只贡献色调** | 「2 dash」 |
| `drop` | 准体积 | ≈ 0.05 ml | 忽略 | 「3 滴」 |
| `barspoon` `tsp` | 体积 | 5 ml | 全额 | 「1 吧勺」 |
| `piece` `leaf` `wedge` `slice` | 计数 | `null` | 固体，占体积不算液体 | 「8 片薄荷叶」 |
| `rim` | 修饰 | `null` | 无 | 「杯口盐圈」 |
| `top_up` | 补满 | **编译期计算** | 填至杯容量 | 「苏打水补满」 |
| `to_taste` | 模糊 | `null` | 忽略 | 「适量」 |

**`top_up` 最需要注意**：实际量 = 杯容量 − 已有液体 − 冰的排水体积，**在动画编译期算出，不存库**。需要 `glassware.capacity_ml` 与冰的堆积孔隙率——满杯方冰能容纳的液体约为杯容量的 40~45%，但随冰型变化很大（crushed 更密实），所以写成 `ice.displacementFactor` 可调参数，**别拍死在代码里**。

因此 `top_up` **没有 `amount` 字段**。zod schema 必须用 discriminated union 约束：体积单位必须有 `amount`；计数单位 `amount` 必须是正整数；`top_up`/`to_taste`/`rim` 禁止出现 `amount`。**不写这层约束，v2 让模型生成 IR 时一定会吐出 `{ unit: "top_up", amount: 100 }`。**

**展示层换算**：用户设置 `unitPreference: ml | oz`（默认 ml；浏览器 locale 为 `en-US` 时默认 oz）。

- 原生单位 == 偏好单位 → 原样显示，零损失
- 需要换算 → 吸附到该单位实际刻度，加 `≈`，精确值悬停可见
  - → oz：吸附到最近 **¼ oz**，分数显示（`≈ ¾ oz`），美式酒吧惯例不写小数
  - → ml：取整到最近 5 ml

吸附看似失真，其实相反：**量酒器（jigger）的实际刻度本身就是 ¼ oz 级别**，显示 `0.744 oz` 是假精度，`≈ ¾ oz` 才是调酒师真正会倒的量。

**「按份」显示**：支持，但作为**显示模式而非存储模式**。存储始终是绝对量（30/30/30 ml），配方页提供"按份"开关自动约简成 `1 : 1 : 1`。**只在比例接近简单整数比时（容差 5%）才显示该开关**——45/20/15 约简成 `3 : 1.33 : 1` 毫无可读性，那就别提供。另提供缩放控件（改总量或改杯数），`dash`/`leaf` 按整数向上取。

配方页因此有两组无损切换（`ml ⇄ oz`、`绝对量 ⇄ 按份`）+ 份数滑块，**全部纯前端计算，后端不参与**。

## ADR-015 封面图：前端截帧上传

**结论**：用户发布时前端已渲染实时预览，直接 `canvas.toBlob()` 截一帧，走预签名 URL 直传对象存储。

**理由**：这原本是 Go 方案最大的坎——封面图 = 跑 `animator-core` 取末帧 → SVG → PNG，而 `animator-core` 是 TS，服务端做就得挂 Node 进程或 headless Chrome。交给前端后，**服务端零渲染负担，连 Node 都不用装**。

## ADR-016 v1 范围：需求 1~5

**结论**：v1 做需求 1~5（原料库 / 经典配方动画 / 注册发布 / 点赞评论关注搜索 / 酒单）。需求 6、7（AI）入 v2。

**冷启动**：v1 没有 AI 也没有用户，首页是空的。需要约 150~250 个原料条目 + 30~80 款经典配方 IR。**开发期用 AI 批量生成这批种子数据**——属于离线数据准备，不是"向公众提供生成式 AI 服务"，完全不碰 ADR-008 担心的合规问题。配比是公开事实不涉版权，文字描述自己重写。冷启动与 v1 工作量同时解决。

## ADR-019 渲染器：Canvas 2D，不用 SVG

**结论**：`animator-web` 用 **Canvas 2D** 作为唯一 Web 绘制后端。SVG 不参与。

**这条是在写动画原型的过程中修正的**（初稿方案是「SVG 为主 + Canvas 粒子叠加」）。

**理由**：

1. **液层要裁剪到曲面杯型内腔。** Canvas 的 `clip(Path2D)` 一行搞定；SVG 要 `clipPath` + 多段 `linearGradient`，层数变化时还要增删 DOM 节点。
2. **粒子。** 几百个气泡当 DOM 节点动画远慢于 Canvas 绘制，且每帧增删节点会触发布局。
3. **SVG 的优势在这里用不上。** 杯型是从数值剖面**算**出来的，不是手绘路径，所以矢量可编辑性没价值；无障碍性来自自动生成的文字步骤（规范 §8），不来自图形。
4. **Skia 移植成本更低。** Skia 是 canvas 式的即时模式 API，和 Canvas2D 的距离远小于和 SVG 的距离 —— 直接降低 ADR-005 候选 B 的成本。
5. **封面图截帧本来就是 `canvas.toBlob()`**（ADR-015），一致。

**代价**：Canvas 内容对搜索引擎和读屏软件不可见。但配方页的 SEO 与无障碍靠的是标题、描述、原料表、文字步骤 —— 这些都是真 DOM。动画是增强，不是内容载体。

## ADR-020 `recipe-ir` 拆出零 zod 的 `/core` 子入口

**结论**：`@shaker/recipe-ir` 提供两个入口：

```
@shaker/recipe-ir        全量，含 zod schema —— 编辑器、后端校验、种子数据用
@shaker/recipe-ir/core   零 zod 运行时依赖 —— 播放器、渲染器、配方浏览页用
```

`animator-core` 与 `animator-web` 只许引 `/core`。

**理由（实测数字）**：

| bundle | minified | gzip |
| --- | --- | --- |
| 只读播放路径，引 barrel 入口 | 487 KB | **107 KB** |
| 只读播放路径，引 `/core` | 40 KB | **14.3 KB** |
| 完整原型（含编辑器与校验） | 513 KB | 116 KB |

**7.5 倍差距，而且省的正是 99% 访客走的路径**（浏览配方，不发布）。

根因是 barrel 导出：`index.ts` 的 `export * from "./ir.ts"` 无条件把 zod 拉进 bundle，尽管纯数学模块（`glass` / `color` / `units` / `physics`）本来就零 zod 依赖。esbuild 无法 tree-shake 掉 —— `z.enum(...)` 这类调用必须执行。

为此做的两处结构调整：

- `containersUsed` / `slotsReferenced` 从 `ir.ts` 迁到 **`ir-utils.ts`**（只依赖类型）。它们原先住在 zod 文件里，`validate.ts` 运行时引用它们就会把 zod 拖回来。
- `core.ts` **故意不导出** `ACTIONS` / `UNITS` 这类常量数组 —— 它们住在 `vocab.ts`，那个文件顶层 `import zod`。播放路径目前不需要；真需要时再把纯数组拆成独立文件。

**CI 应加一条检查**：`@shaker/animator-core` 与 `@shaker/animator-web` 的依赖图里不允许出现 `zod`。这条纪律和「`animator-core` 不许 import 渲染 API」同级。

## ADR-021 工具链约束：不用 TS 参数属性

**结论**：全仓禁用 TypeScript **参数属性**（`constructor(private x: T)`），以及 enum、namespace 等需要类型导向代码生成的语法。

**理由**：`node --experimental-strip-types` 是 strip-only 模式 —— 它只删类型标注，不做语义转换。参数属性会直接报 `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`。

这个约束让所有纯 TS 包（`recipe-ir`、`animator-core`、`seed`）能被 node **直接跑测试**，不需要构建步骤。这个便利值得换掉一点语法糖。
