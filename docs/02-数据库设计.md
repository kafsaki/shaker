# 数据库设计

DDL 见 `apps/api/db/migrations/00001_init.sql`（goose 迁移，可执行）。本文只写**为什么**——DDL 里的注释写了关键决定，这里补全局性的取舍。

> **本文档对应的 DDL 尚未在真实 Postgres 上执行验证**——开发机当前没有 Docker/Postgres/WSL。
> 装好 Docker 后按 §7 验证。

数据库设计是 ADR-018 不可逆性排序里的**第一位**：改一张有百万行的表比换后端语言痛苦一个量级。所以这里的谨慎是刻意的。

---

## 1. 全局约定

| 约定 | 选择 | 理由 |
| --- | --- | --- |
| 主键 | **UUIDv7**（Go 侧生成） | 时间有序 → 索引局部性好；可安全暴露在 URL；不需要序列协调。PG 17 没内置 `uuidv7()`，不为此引扩展 |
| 词表主键 | **text slug** | `gin-london-dry` 可读、可写死在种子数据里、便于 IR 直接引用 |
| 时间 | **一律 `timestamptz`** | 永不用 `timestamp` |
| 删除 | **软删除 `deleted_at`** 用于 UGC；词表硬删 | UGC 需要可恢复与审计；词表由运营维护，删了就是删了 |
| 金额/度量 | `numeric` | 浮点在酒精度和用量上会累积误差 |
| 枚举 | 见 §2 | |

## 2. 为什么只有五个原生枚举

只为**纯数据库概念**建 PG 枚举：`recipe_status`、`recipe_source`、`menu_visibility`、`report_status`、`user_status`。

`family`、`category`、`role`、`unit`、`method`、`iba_category` 这些**故意用 `text`**，因为它们的值域已经在 `packages/recipe-ir` 的 zod 里定义了（ADR-002 的闭集词表）。再建一份 PG 枚举就有了**第三个真相源**（zod → JSON Schema → PG 枚举），三者必然漂移。

这些字段由应用层按 JSON Schema 校验。少数加了 `CHECK`（如 `iba_category`、`lang`）是因为值域极小且几乎不会变。

## 3. 三个关键结构决定

### 3.1 `ir` 存 JSONB，不拆 steps 表

配方是**原子读写单元**——永远整份取出、整份写回。拆成 `steps` / `step_items` 表只会带来 N+1 查询和事务复杂度，换不来任何查询能力（因为没人会"查所有用了 SHAKE 的第三步"）。

需要查询的维度用投影表解决，见下。

### 3.2 `recipe_ingredients` 是投影表，不是真相源

保存配方时由应用层从 `ir.ingredients` 重建（`DELETE` + `INSERT`，在同一事务里）。

**存在理由**是三个真实查询：

```sql
-- 「用到某原料的配方」（原料百科反查，需求 1）
SELECT r.* FROM recipes r
  JOIN recipe_ingredients ri ON ri.recipe_id = r.id
 WHERE ri.ingredient_id = 'gin-london-dry' AND r.status = 'published'
 ORDER BY r.hot_score DESC;

-- 「以金酒为基酒」而非「任何位置含金酒」
 WHERE ri.ingredient_id = 'gin-london-dry' AND ri.role = 'base'

-- 「含 40ml 以上金酒」
 WHERE ri.ingredient_id = 'gin-london-dry' AND ri.amount_ml >= 40
```

在 JSONB 上做这些要用 GIN + 容器操作符，写起来别扭且数值范围筛选走不了索引。

主键是 `(recipe_id, slot)` 而非 `(recipe_id, ingredient_id)`——**同一配方可以有两种朗姆**（Mai Tai 就是），后者会主键冲突。

### 3.3 计数冗余 + 对账

`like_count` / `comment_count` / `collect_count` / `derived_count` / `follower_count` 等冗余在主表上。

维护方式：**与源表写入在同一事务里做原子 `UPDATE`**（不用触发器——用 sqlc 写显式 SQL 更好测、更好读），另有 river 周期任务从源表重算对账。

`likes` / `comment_likes` / `follows` / `menu_items` 的**主键本身就防重复**（`PRIMARY KEY (user_id, recipe_id)`），所以"双击点赞两次"在数据库层就不可能发生，不依赖应用层判重。

## 4. 变体双机制的索引（ADR-013）

```sql
-- 一个经典只能有一个权威条目
CREATE UNIQUE INDEX recipes_canonical_key ON recipes (classic_key) WHERE is_canonical;
-- 经典页聚合变体 + Feed 层折叠
CREATE INDEX recipes_classic_idx ON recipes (classic_key, hot_score DESC)
  WHERE classic_key IS NOT NULL AND status = 'published';
CONSTRAINT recipes_canonical_needs_key CHECK (NOT is_canonical OR classic_key IS NOT NULL)
```

偏唯一索引（partial unique index）是这里的关键手法：一个 `classic_key` 下可以有 127 个社区变体，但只能有一个 `is_canonical = true`。数据库层面就保证了，不靠应用层自律。

**Feed 层的"同 classic_key 单页最多 2 条"折叠规则不在数据库里**——那是查询/应用层的事，放在那里调参便宜，数据模型不动。

## 5. 索引策略：大量偏索引

几乎所有 Feed 与筛选索引都带 `WHERE status = 'published' AND deleted_at IS NULL`：

```sql
CREATE INDEX recipes_hot_idx ON recipes (hot_score DESC, id)
  WHERE status = 'published' AND deleted_at IS NULL;
```

理由：草稿和已删除配方永远不出现在任何公开列表里。偏索引让索引只覆盖真正被扫描的行——体积小、缓存命中率高，而草稿量在 UGC 站里通常不小。

热度公式（由 river worker 周期重算写回 `hot_score`）：

```
hot = (like_count + 2·collect_count + 0.5·comment_count + 1) / (age_hours + 2)^1.6
```

`collect_count` 权重最高，因为"加入酒单"比点赞更能表达"我真想做这杯"。

## 6. 搜索（ADR-012）

需求 4 的四种搜索全是**短词场景**，`pg_trgm` 全部覆盖：

| 搜索 | 索引 |
| --- | --- |
| 配方名 | `recipes.title` GIN trgm |
| 用户名 | `users.handle` + `users.display_name` GIN trgm |
| 原料名 | `ingredients.name_zh` / `name_en` GIN trgm + **`ingredient_aliases.alias` GIN trgm** |
| 按原料筛配方 | `recipe_ingredients (ingredient_id, amount_ml)` B-tree |

**别名用独立表 `ingredient_aliases` 而不是 `text[]`**——这是相对 ADR-011 初稿的一处修正：`pg_trgm` 索引不能直接作用在数组上，而"按原料名搜索"正是需求 4 的一项。这张表同时是 v2 让模型对齐原料 ID 的依据（ADR-008 的两段式抽取第二步）。

英文长文描述另挂 `search_en tsvector`。中文分词（`zhparser` / `pg_bigm`）要自己编译，在本地 Docker 里很折腾，而 trgm 对中文短词已经够用。十万级配方以内不需要 ES。

## 9. 两处细节，值得单独说

### 9.1 `menu_items.position` 用 `numeric(20,10)` 而非 `integer`

拖拽重排时可以取两项之间的中点插进去（`(prev + next) / 2`），不必重写整个列表的序号。整数方案在"把第 50 项拖到第 2 位"时要 UPDATE 49 行。

精度会在反复插入同一位置时耗尽（约 30 次后），所以配一个 river 任务在精度过低时重整该酒单序号。

### 9.2 预签名上传是两步

`media_assets.committed_at` 为空 = 已建记录但客户端还没传完。流程：

```
1. POST /media/upload-url  → 建 pending 记录 + 返回预签名 URL
2. 客户端直传对象存储      （不经过后端）
3. 确认接口               → 置 committed_at
```

没确认的记录由 river 周期任务连同对象一起清理，避免孤儿文件堆积。这个两步流程是"前端截帧上传封面图"（ADR-015）能安全工作的前提。

对象存储 key 规范（ADR-018 列为半不可逆，所以写死在 DDL 注释里）：

```
recipes/{recipe_id}/cover-{revision}.png
users/{user_id}/avatar-{content_hash}.jpg
menus/{menu_id}/cover-{content_hash}.jpg
```

key 里带 revision 或内容哈希，**CDN 缓存靠换 URL 失效，不依赖 purge**。
